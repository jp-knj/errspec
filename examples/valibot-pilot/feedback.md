# 最初の利用で確かめること

目的は、既存プロジェクトの失敗時の検証を1ケースだけ管理して、追加の設定を維持する価値があるかを確かめることです。[自動検証の結果](README.md)は再現性の確認であり、利用者の評価はこれから集めます。

## 試す範囲

まずknj自身のプロジェクトで試し、その後、同意した開発者に同じ課題を渡します。TypeScriptの有限な文字列タグを持つエラー型と、BunまたはVitestのテストがあるプロジェクトを対象にします。APIエラーのHTTP応答への変換や、依存先の失敗後に副作用を起こさない処理など、既に期待動作を説明できるケースを1つ選びます。

対象の型に複数のタグがある場合、`init`は全タグのTODOを生成します。未完成のケースがある間は全体のverifyが失敗します。初回から多数のケースを実装する必要があるなら、その負担も記録し、試用のためだけに製品コードの型を変えないでください。

試用者には、[CLIの導入手順](../../packages/cli/README.md)と対応OSの配布物を渡します。npmには未公開です。リポジトリが非公開のため、外部の試用者へ渡す成果物と方法は別途決めます。この文書の追加で配布や連絡が実行されることはありません。

## 実施手順

作業用ブランチで実施し、テスト対象プロジェクトの通常の依存を先にインストールします。OSに合うCLI・testkit・nativeの3つのtarballを一緒に追加してください。Node.jsと選んだランナーが必要です。

以下はBun、`_tag`識別子、`Failure`型の例です。パスと型名は対象に合わせます。Vitestなら`--runner vitest`を使います。

```sh
./node_modules/.bin/errspec init \
  --project tsconfig.json --source src/errors.ts --export Failure --runner bun
./node_modules/.bin/errspec verify --runner bun --only-contract-tests
```

1. 生成されたTODOが失敗することを確認します。型を選べない場合は`scan --project tsconfig.json --format json`を試し、選べたか、候補を探す手間を記録します。
2. 期待動作を一文で書き、設定の`expect`と必須比較IDを編集します。生成テストで実際のアプリケーションを呼び、`s.fault`と`s.check`を記入してverifyを通します。型に複数タグがあれば他のケースも必要です。
3. 期待動作と必須比較を人が確認してからbaselineを作ります。

```sh
./node_modules/.bin/errspec snapshot --out errspec.baseline.json
./node_modules/.bin/errspec verify --runner bun --only-contract-tests \
  --baseline errspec.baseline.json --strict-baseline
```

4. 複数ある必須比較のうち1つだけをテストから削除します。通常のBun/Vitestとerrspecを実行し、通常のテストが通ってもerrspecが`EC010`で止まるか確認します。比較が1つだけなら、削除するとtestkit自体が失敗するため、この違いを試せません。
5. 同じ比較IDを設定の`observe.assertions`からも削除します。通常のverifyは通り、baselineを指定したstrict verifyが`EC014`で止まるか確認します。baselineは作り直さず、設定とテストを元に戻してstrict verifyを通します。

途中で詰まったら、助けを求める前のコマンド・表示・期待した操作を残します。進行役が説明した内容も記録します。成功までの所要時間はインストール待ち・作業・支援を分け、未完了なら未完了として扱います。

## フィードバック後の判断

導入で止まるなら、最初に止まった手順を改善します。型を選ぶところで止まるなら候補の表示を、シナリオ実装で止まるなら生成例とAPIを見直します。保護の価値が伝わっても二重管理が負担なら、設定を増やす前に省略できる記述を調べます。

継続利用したいという回答が出ても、実際のPRで維持できるかは別に確認します。少人数の試用結果を一般的な需要や導入時間の保証へ広げません。
